# 1. Flaws

**Verdict: revise before implementation.** Review of the proposed design in `docs/reviews/P2P-COUNCIL-BRIEF.md:35`, against checkout `4f43e29d8c42dc1bf1f579ea8fe02f9800988820` on 2026-10-01. The federation feature is unimplemented; findings below are concrete integration failures the proposal must prevent, not claims of an exploitable existing network service. Source inspection only: no Cargo build/test, live peer connection or exploit was run. The report was written after the initial pass and refined in place. Findings are ranked by impact, then implementation dependency.

**F1 — High: SEC-7 is unsuitable for granting durable remote access; protecting only Settings does not fix it.**

- **Evidence:** `crates/axon-bus/src/serve.rs:219` permits GET with a loopback Host alone; `crates/axon-bus/src/serve.rs:251` embeds the token in the page; `crates/axon-bus/src/serve.rs:222` checks token and caller-supplied Origin on mutations. `crates/axon-bus/src/serve.rs:314` forwards a caller-selected `from_id` from `/api/msg`. `docs/BUS-PLAN.md:287` explicitly accepts this for single-user local operation.
- **Failure/impact:** another local OS account can fetch the page, supply the correct Origin with a non-browser client, and pair its own machine or expand grants. Even if only the new Settings endpoints receive stronger auth, the existing send endpoint could impersonate a local agent and send to already-shared remote inboxes. Trust survives the local attacker leaving. Host/Origin protect against browser attacks; they do not authenticate a local OS user.
- **Smallest fix:** before enabling federation, require an owner-authenticated browser session for all dynamic dashboard reads, streams and writes, including existing send routes. Bootstrap it through an owner-only file or the owning terminal; never return its credential in unauthenticated HTML. Reuse the secure fresh-file pattern at `crates/axon-bus/src/serve.rs:110`, keep Host/Origin/CSP checks, and keep the dashboard on loopback. The public static shell may remain public. Use a header capability scoped to the exact dashboard origin, not a bearer in query parameters; protect streamed responses too. Make secret-bearing responses non-cacheable and preserve the service worker's exclusion of dashboard/API data (`crates/axon-bus/ui/sw.js:1`). Existing page tokens must not authorize federation operations. This is an OS-account boundary, not protection against malicious code running as the owner or root.

**F2 — High: “never trigger the relay” is not a prompt-injection guarantee.**

- **Evidence:** `crates/axon-bus/src/msg.rs:23` accepts `redirect` and `handoff` as well as `stop`; `crates/axon-bus/src/msg.rs:145` gives stop messages actual subtree effects. `crates/axon-bus/src/msg.rs:454` frames bodies as untrusted, but `crates/axon-bus/src/msg.rs:459` interpolates body, sender, thread and refs into text. `crates/axon-bus/src/roster.rs:110` interpolates roles/IDs into introductory context. `crates/axon-bus/src/hook.rs:365` invokes the relay for a later local tool call; `crates/axon-bus/src/relay.rs:18` permits send, grant, link, claim and other verbs outside the sandbox. `crates/axon-bus/src/cli_guard.rs:1` explicitly disclaims a complete sandbox boundary.
- **Failure/impact:** a remote `sync` body can ask the local model to exfiltrate data or run a local bus command. The model can subsequently choose that command, activating the ordinary relay. A body containing `[end of peer message]`, a malicious display name or a crafted ref can also impersonate surrounding instructions if inserted raw. Banning a wire-level stop is necessary but does not contain semantic attacks or agent-driven forwarding into another local project.
- **Smallest fix:** separate network ingestion from hook/tool execution. For v1 allow only informational `sync`, `question`, `answer`, `ack`; reject stop, redirect, handoff, budget, claim, link/grant, spawn and unknown operations. Bind sender provenance to the authenticated peer, never payload text; frame **all** remote fields, including discovery labels/refs, as quoted data with escaped controls/delimiters. Generate reply command IDs locally. Update `crates/axon-bus/src/guide.rs:22` and the intro to distinguish a remote collaborator from the local owner and prohibit treating messages as approval. Never auto-execute, auto-forward, fetch refs or grant authority from inbound text. Keep owner operations outside agent-accessible capabilities. Framing reduces risk; it does not prove a model will ignore malicious text. Strong containment of arbitrary agent actions requires an actual sandbox/tool authorization boundary, which this proposal does not add.

**F3 — High: remote URL matching does not establish project membership, and current registry data is not a live authorization oracle.**

- **Evidence:** the proposed key is a normalized remote URL (`docs/reviews/P2P-COUNCIL-BRIEF.md:46`). Local identity is canonical git common-dir grouping (`crates/axon-bus/src/snapshot.rs:29`, `crates/axon-bus/src/snapshot.rs:66`). Existing registrations retain the first non-null cwd through `cwd=coalesce(cwd, ?5)` (`crates/axon-bus/src/registry.rs:52`), and snapshots cache checkout resolution by cwd (`crates/axon-bus/src/snapshot.rs:136`). Children can belong to a different repo than their parent (`crates/axon-bus/src/snapshot.rs:253`).
- **Failure/impact:** a URL supplied by the peer proves nothing about its checkout. SSH aliases, HTTPS spelling, renamed repositories, forks, multiple remotes and no-remote repos also make automatic matching unreliable. Authorizing from the displayed root or cached initial cwd can grant a child or moved session access to the wrong project. Merely claiming a granted URL is **not** a bypass if the receiver independently enforces a local binding; that binding, rather than URL normalization, is the missing authority.
- **Smallest fix:** create an opaque project-sharing ID scoped to a particular paired peer; each owner explicitly binds it to a local canonical repository. URLs are credential-stripped matching hints only. At local registration bind each agent to approved local project membership; on relevant cwd changes refresh it or suspend remote access pending re-registration. Recheck current local sender/recipient membership, direction and grant when enqueueing, accepting and delivering. Unknown/unresolvable membership fails closed. Worktrees may inherit their common-dir binding; separate clones/forks require explicit selection, even with identical remotes. A malicious remote owner can lie about its own agent's repo; the enforceable guarantee is which **local** projects that authenticated peer may reach, not remote filesystem attestation.

**F4 — High: `<peer>:<id>` is a display syntax, not a sufficient identity/routing/thread model.**

- **Evidence:** `crates/axon-bus/src/store.rs:11` keys agents by one local string; `crates/axon-bus/src/store.rs:53` stores local sender/recipient references. `crates/axon-bus/src/msg.rs:85` requires registered agents and then `crates/axon-bus/src/route.rs:115` authorizes local tree/link/grant edges. Sequence assignment uses the thread string alone (`crates/axon-bus/src/msg.rs:121`). Replies look up a local message ID (`crates/axon-bus/src/msg.rs:239`); awaited answers match thread plus refs (`crates/axon-bus/src/msg.rs:286`).
- **Failure/impact:** inserting remote agents as normal local roots just to satisfy `msg::send` can create unintended local routing authority. Peer names can change or collide; remote IDs/thread IDs can collide with local ones or another peer's. Blindly retaining a peer-supplied question ID can attach an answer to someone else's conversation. The proposal also silently changes the current root-to-root consent model by advertising every shared-project session as directly reachable.
- **Smallest fix:** use typed local versus remote principals. Remote identity is `(pinned peer identity, pairing generation, remote session instance)`; the human name is only a label. Bind conversation/message mappings to that identity, share ID and participants. Resolve replies using a persisted wire-to-local ID mapping and require the answerer to be the original addressee; an application ack cannot acknowledge another message. Do not expose local route suggestions to unauthorized peers. Define a new explicit federation edge: recommend direct messaging only between locally registered agents covered by the owners' matching project-direction grants, with no inherited local tree, link or grant powers and no transit to a third peer. Document that deliberate extension in the intro/guide; preserve existing local routing unchanged.

**F5 — High: the pairing description lacks endpoint discovery, a complete authorization transition and downgrade rules.**

- **Evidence:** `docs/reviews/P2P-COUNCIL-BRIEF.md:38` gives Join only a short code, but B at `docs/reviews/P2P-COUNCIL-BRIEF.md:43` supplies neither rendezvous nor discovery. The existing token generator supplies strong randomness (`crates/axon-bus/src/serve.rs:103`) but there is no pairing protocol to reuse. `crates/axon-bus/src/serve.rs:92` is a privileged local HTTP router, not an enrollment service.
- **Failure/impact:** a code cannot locate the other Axon under B. Treating PAKE success, a displayed fingerprint, or knowledge of a tailnet address as completed owner approval permits premature enrollment or trust in the wrong identity. Short codes also need bounded online attempts. An attacker can exploit any fallback from pin failure to first-use trust, plaintext, an older application protocol or weaker pairing.
- **Smallest fix:** specify an endpoint-bearing invitation and an explicit pending/confirmed/expired/consumed state machine. Bind enrollment to both proven keys, roles, invite ID and protocol version; consume the invitation atomically for one joining identity; grant zero projects. Select one protocol/version policy and fail closed on mismatch. If short codes remain, use a maintained PAKE with key confirmation and an attempt budget; key confirmation is part of SPAKE2, not an optional fingerprint UI step ([RFC 9382, sections 3–4](https://www.rfc-editor.org/rfc/rfc9382.html#section-4)). Do not create a public rendezvous service merely to preserve a short-code aesthetic. The simpler recommended pairing is in section 2.

**F6 — High: pause, revoke and project unsharing must govern existing sessions and queued work, not just handshakes.**

- **Evidence:** the proposed schema has `revoked_at` but no durable paused state (`docs/reviews/P2P-COUNCIL-BRIEF.md:46`), while the UI promises Disconnect/pause (`docs/reviews/P2P-COUNCIL-BRIEF.md:57`). The inbound check is at receipt (`docs/reviews/P2P-COUNCIL-BRIEF.md:50`). Existing delivery selects all undelivered non-stop rows without authorization/expiry checks (`crates/axon-bus/src/msg.rs:434`).
- **Failure/impact:** dropping a socket triggers retry and reconnects after the owner clicked Disconnect. A valid handshake cached in memory can outlive Remove. A message already in the inbox or outbox can be delivered after unsharing, even if all subsequent inbound packets are checked correctly. Re-pairing the same key can resurrect old queued messages if identity alone is the queue key.
- **Smallest fix:** persist paused state and revocation tombstones; use a fresh pairing generation on explicit re-pair. Pause blocks inbound/outbound application traffic and automatic reconnect, retains bounded queues with their original expiry, and requires explicit Resume. Revoke/unshare closes or narrows active sessions and atomically cancels affected pending deliveries. Give each grant episode a revision so unshare/re-share cannot revive frames from the previous authorization. Serialize those changes with acceptance/dequeue and check current policy again before transmission and hook delivery. Send a best-effort authenticated revocation notice, but never wait for it to enforce local denial. The completion boundary is local policy commit: work released before it may already be in transit or a harness. Neither revocation nor expiry retracts text already disclosed; offline remote UI cannot know revocation until contact resumes.

**F7 — High: retry plus a 24-hour TTL is not a delivery protocol.**

- **Evidence:** `docs/reviews/P2P-COUNCIL-BRIEF.md:60` specifies only queue/retry/expiry. Every local insertion creates a new message ID (`crates/axon-bus/src/msg.rs:119`); the message schema has no peer deduplication key or outbox states (`crates/axon-bus/src/store.rs:53`). Hook delivery marks rows before returning output (`crates/axon-bus/src/msg.rs:472`), and `crates/axon-bus/src/hook.rs:351` commits before `crates/axon-bus/src/hook.rs:72` prints. Connections use `synchronous=NORMAL` (`crates/axon-bus/src/store.rs:220`).
- **Failure/impact:** if the receiver commits and its acknowledgment is lost, retry creates a duplicate. A crash after hook commit but before stdout loses the attempted context injection while the DB says delivered. Expiring only the sender outbox leaves stale received questions deliverable later. A received packet, committed inbox row and agent answer are different milestones. WAL/NORMAL also does not promise preservation of every committed transaction across power loss ([SQLite synchronous documentation](https://www.sqlite.org/pragma.html#pragma_synchronous)).
- **Smallest fix:** persist a stable message ID before the first send; atomically commit authenticated inbox data, unique `(peer, pairing generation, message ID)` dedup record and acceptance audit before acknowledging. A repeated ID must have identical canonical content; conflicting content is a protocol error. Separate transport acceptance responses from agent-authored `ack` messages. Give frames a bounded authenticated creation/expiry interval, preserve original expiry on retry, and enforce it at both send and hook delivery; retain dedup records beyond the full permitted replay window. Authentication prevents outsiders changing these fields; it does not make a paired sender's clock trustworthy, so receiver-local time bounds acceptance. Distinguish queued, peer-accepted, hook-prepared, answered, expired, cancelled and permanently rejected. Retry only transient failures with bounded backoff. Disable early application data; TLS 1.3 0-RTT has special replay risks ([RFC 8446, section 8](https://www.rfc-editor.org/rfc/rfc8446.html#section-8)). Use durable commit settings for acknowledged inbox/outbox and security-state changes if claiming power-loss durability; otherwise name the narrower guarantee. Do not promise exactly-once model execution: current hooks have no acknowledgment that context was consumed.

**F8 — High: sharing a project must not export the dashboard snapshot or an entire agent subtree.**

- **Evidence:** the current roster is relatively small: ID, harness, role, status (`crates/axon-bus/src/roster.rs:16`). In contrast, `crates/axon-bus/src/snapshot.rs:262` serializes model, mission, absolute repo path, branch, spend, budgets and narrative. It recursively includes all children at `crates/axon-bus/src/snapshot.rs:249`, with cross-repo badges rather than an access filter. The snapshot also includes observed sessions which cannot receive messages (`crates/axon-bus/src/observed.rs:1`).
- **Failure/impact:** reusing the available snapshot for remote session discovery discloses unrelated-project children, filesystem layout, private tasks and captured content. Even the existing role/harness fields are additional disclosures, not necessary routing information. A paired but ungranted peer must not learn the owner's project inventory by enumerating toggles or IDs.
- **Smallest fix:** define a separate allowlisted discovery DTO, filtered server-side per agent and approved project before serialization. Default to opaque session instance, locally chosen display label, coarse availability and approved share ID; disclose model/harness/role/mission only through a separate explicit choice if ever added. Exclude observed-only sessions, paths, branch, process IDs, usage, budgets, claims, narrative and topology. Paginate and expire discovery; clear cached visibility on unshare/revoke. Keep new peer/project/session names as text in the UI, matching `crates/axon-bus/ui/app.js:1`. `--no-content` is a local capture setting, not authorization to export metadata.

**F9 — High: body length and unspecified “size/rate caps” leave network, database and context amplification open.**

- **Evidence:** `crates/axon-bus/src/msg.rs:71` limits only body characters; `crates/axon-bus/src/msg.rs:138` stores an arbitrary refs array. `crates/axon-bus/src/msg.rs:434` reads the entire pending inbox into a vector and one context string. All bus writes share an immediate transaction lock (`crates/axon-bus/src/store.rs:227`); hooks wait only 150 ms (`crates/axon-bus/src/store.rs:162`).
- **Failure/impact:** a small body with megabytes of refs/labels or thousands of valid messages can exhaust RAM/disk, crowd the model context and spend the recipient's budget. Peer discovery updates or unbounded rejected-message audit writes can also starve unrelated local hooks. A paired peer is authenticated, not resource-trusted.
- **Smallest fix:** cap wire bytes before allocation and bound every decoded field, collection, handshake and discovery page. Add byte/count queue quotas and aggregate plus per-peer/project/recipient rate limits. Bound each hook injection batch; leave overflow pending without marking it delivered. Keep network waits outside SQLite transactions and rate-limit rejection auditing. Preserve stop/budget priority. Refs remain inert, bounded repo-relative metadata: reject absolute paths, traversal, URI schemes and malformed revisions; never run git, shell, file reads or URL fetches from a received ref. Reference availability/revision mismatch is informational, not an instruction to fetch or checkout code.

**F10 — Medium: “0600 long-lived key” is incomplete on supported platforms and after compromise.**

- **Evidence:** `docs/reviews/P2P-COUNCIL-BRIEF.md:37` specifies only mode 0600. The app promises macOS/Linux/Windows (`docs/BUS-PLAN.md:117`), but existing permission handling ignores Unix chmod errors and is a no-op off Unix (`crates/axon-core/src/store.rs:307`). The safer ready-file helper uses exclusive creation but its mode is also Unix-only (`crates/axon-bus/src/serve.rs:112`).
- **Failure/impact:** copying these helpers blindly may leave a key readable under a broad Windows ACL or proceed after failed permission changes. A stolen key remains a valid peer credential until revoked; reconnecting at the same address or accepting a key-change notice does not recover trust. Restoring an old database can restore old grants/revocation state.
- **Smallest fix:** exclusive, atomic key creation in an owner-only directory, checked ownership/permissions on Unix and an explicit owner-only ACL/secure storage policy on Windows; refuse federation if protection fails. Separate the identity key from browser/invite secrets. Missing/corrupt keys disable federation with a clear recovery action, never silently replace the identity. For v1 recover by removing the old identity and explicit fresh pairing with no inherited grants/queued work; do not auto-rotate based on the old possibly-stolen key or address. Any supported restore flow must invalidate old pairings/grants and require owner-confirmed recovery. Arbitrary rollback of all local files cannot be reliably detected without an external trusted checkpoint; do not claim that stronger guarantee. Same-user compromise remains outside file-mode protection.

**F11 — Medium: server lifetime and health need a concrete owner; hooks cannot be network workers.**

- **Evidence:** `src/main.rs:67` dispatches hooks before creating Tokio. The dashboard runtime starts at `src/main.rs:100`, mounts the bus at `src/main.rs:125`, and binds loopback at `src/main.rs:126`. `crates/axon-bus/src/serve.rs:56` offers another server entry point. The relay has a 10-second kill deadline (`crates/axon-bus/src/relay.rs:25`) and explicitly rejects waiting `ask` (`crates/axon-bus/src/relay.rs:66`). Current `/api/health` returns a static `ok` (`src/server.rs:65`).
- **Failure/impact:** dialing/retrying inside send hooks stalls tools and duplicates listeners. Starting a worker in every router construction can create competing services for one database, especially through the serve alias or another port. A healthy HTTP dashboard says nothing about peer authentication, heartbeat or delivery. B also cannot connect arbitrary unreachable NATed machines merely by exchanging codes.
- **Smallest fix:** one federation service per data directory owned by the long-running server, with an OS-lifetime singleton lock, separate authenticated network listener, bounded background workers and shutdown handling. Support both server entry paths through the same service; a second instance must report the existing owner rather than start another worker. CLI/hooks only validate and commit local queue work. Stopping Axon stops networking; closing the browser does not. Surface that distinction in Settings. Peer-service failure must leave the local dashboard/bus usable and report offline/error. Choose B only with an explicit reachable-network prerequisite; see section 2.

**F12 — Medium: the existing hash chain cannot by itself provide the promised peer audit evidence.**

- **Evidence:** `crates/axon-bus/src/store.rs:144` stores event actor/verb/subject and payload hash, not the payload. `crates/axon-bus/src/store.rs:263` hashes and discards the supplied payload; the send event at `crates/axon-bus/src/msg.rs:163` has no authenticated peer or project. `crates/axon-bus/src/store.rs:304` already says an external chain head is needed to detect tail truncation.
- **Failure/impact:** putting peer/project/rejection reason only inside the hashed payload loses the inspectable explanation. A human-readable peer name is mutable and cannot establish which pinned key performed an action. Hash chaining is not a peer signature or proof against an owner who can rewrite the database.
- **Smallest fix:** persist minimal structured federation audit metadata alongside the existing chain: immutable peer-key fingerprint, pairing generation, share ID, message ID, direction, decision/reason and local timestamp, with the owner as actor for grant changes. Atomically couple it to accepted messages and policy mutations. Exclude private keys, invitation/browser secrets, message bodies and raw credential-bearing URLs. Bound unauthenticated failure logs. Reuse the chain; do not invent a distributed ledger or claim third-party non-repudiation.

# 2. Decisions

| Decision | Recommendation and repository-grounded reason |
|---|---|
| Transport | **B first: one TLS 1.3 implementation with mutually authenticated pinned Ed25519 identities**, including proof of private-key possession, a fixed application protocol identifier/version and no 0-RTT. Choose mTLS rather than leaving “mTLS/Noise” unresolved; do not implement a bespoke handshake. Keep the dashboard loopback-only (`src/main.rs:126`) and use a separate explicitly configured LAN/tailnet listener. Addresses are locators, never identity. A shared network is a deployment prerequisite, not verified by this audit. If connectivity without an existing reachable network is required, choose **A instead of B**, using its maintained traversal/relay machinery. Do not prebuild both. **Reject C initially**: hosting, availability and traffic metadata are extra responsibilities with no requirement here (`docs/reviews/P2P-COUNCIL-BRIEF.md:29`). “Ciphertext only” does not mean metadata-free: iroh documents relay visibility of connection timing, IPs and volume ([iroh security documentation](https://docs.iroh.computer/deployment/security-privacy)). |
| Pairing | **Use an endpoint-bearing, high-entropy one-time invitation pasted in Settings; PAKE is unnecessary for that secret.** Generate a 256-bit random secret, invite ID and 10-minute expiry, with the inviter's public-key pin, endpoint and protocol version. The recipient gets it through an independently trusted human channel. Verify the inviter pin before disclosing the secret; prove the joining key through the vetted authenticated protocol; then both Settings pages explicitly confirm the identity before trust becomes active. The enrollment path admits pending identities only for enrollment, with no discovery/messages. Consume once for one joining key; tolerate a retry only as recovery of that same pending pairing. No automatic first-use trust or pin replacement. If a short manually typed code is a real requirement, use a maintained SPAKE2/CPace implementation plus bounded attempts, transcript-bound keys and explicit confirmation; do not replace PAKE with hashing a short code. Existing randomness/file patterns are at `crates/axon-bus/src/serve.rs:103` and `crates/axon-bus/src/serve.rs:110`. |
| Project key and grants | **Opaque share ID scoped to the peer/pairing, explicitly mapped to a local project on each side.** Keep canonical common-dir identity local (`crates/axon-bus/src/snapshot.rs:66`), with explicit binding for a project without a remote; no `.git/config` URL can self-authorize. Model inbound/outbound grants separately: A→B requires A's outbound permission and B's inbound permission; a reply also needs the reverse direction, not implicit authority from having received a question. Pairing starts with no grants or discovery. Refresh/reject stale registration membership rather than using cached UI identity (`crates/axon-bus/src/registry.rs:52`). |
| Remote routing and wire surface | **Explicit project federation edges, separate remote principals, no transitive routing.** Allow an owner-approved project's eligible local agents to message approved remote instances directly; do not synthesize local parent/link/grant rows to achieve this (`crates/axon-bus/src/route.rs:115`). Only sync/question/answer/ack cross the boundary. An envelope includes version, message ID, pairing generation, share ID and grant revision, source/target instance, mapped thread/reply ID, creation/expiry, body and bounded refs. Derive peer identity from the authenticated connection. Unknown operations/fields fail closed; local-only capabilities cannot be negotiated into the remote allowlist. |
| Disconnect versus Remove | **Keep both and add an explicit paused state and Resume action.** Disconnect pauses traffic/retries across restarts and freezes delivery without extending expiry. Remove revokes locally immediately, closes sessions, cancels affected queues and invalidates discovery; it retains a minimal tombstone/audit record. Re-pairing starts a new generation with zero grants. An offline peer cannot acknowledge removal, and the UI must not claim remote erasure (`docs/reviews/P2P-COUNCIL-BRIEF.md:57`, `crates/axon-bus/src/msg.rs:434`). |
| Minimum health | Show pending pairing / connected / reconnecting / offline / paused / revoked / incompatible or error; last successful authenticated handshake, last authenticated heartbeat age, RTT when fresh, last error/next retry, queued count/bytes/oldest age, peer-accepted and received counts, and expired/rejected/cancelled counts. Label counters by stage and lifetime; retries must not inflate unique-message totals. Show grant direction separately from connection state. Recommend 10-second heartbeats and stale/offline by 30 seconds without an authenticated response; never leave a stale RTT looking current. Updates need live service state even when the message DB does not change (`crates/axon-bus/src/serve.rs:131`). A connected peer with an idle/unhooked agent is not confirmed delivery: `crates/axon-bus/src/gate.rs:77` and `crates/axon-bus/src/msg.rs:472` establish only local hook preparation. |
| Ownership and packaging | **A small module family inside `axon-bus`, started once by the existing server**, using the same database and explicit schema migration. Split transport, policy/persistence and dashboard handlers as needed; do not enlarge `serve.rs` into a second bus or create a separate daemon. The bus already owns the relevant surfaces (`crates/axon-bus/src/lib.rs:6`, `crates/axon-bus/Cargo.toml:30`). A new crate becomes justified only by an independently reusable protocol or a concrete dependency/build constraint, not by the existence of networking. |

**Proposed bounded baseline for acceptance tests, not measured capacity:** 8 KiB maximum encoded frame, 400 Unicode scalar values per body, at most eight refs of 256 UTF-8 bytes each, protocol IDs at most 128 bytes with a restricted grammar, 100 sessions per discovery page/1,000 per peer, and bounded printable display labels. Start with per-peer 10 application messages/s and burst 20, plus per-recipient 2/s and burst 5; apply aggregate limits so adding identities cannot bypass the cap. Bound pending work to 1,000 messages/8 MiB per peer, 100 messages per recipient and 32 MiB globally, counting inbound and outbound data. A hook emits at most 20 messages/16 KiB of rendered remote context. Cap in-progress handshakes at four with a five-second timeout, keep one active invitation per owner with at most five failed authentication attempts, and use jittered retry backoff capped at 60 seconds. Bound message lifetime to 24 hours, reject creation timestamps more than two minutes in the receiver's future, and retain dedup records for at least 25 hours after acceptance; still reject expired envelopes after dedup cleanup. These are intentionally small defaults for two developers; freeze any revised values before tests are written. The existing 400-character limit and 150 ms hook lock timeout are the integration constraints (`crates/axon-bus/src/msg.rs:14`, `crates/axon-bus/src/store.rs:162`).

**Properties to preserve, checked in source:** the dashboard binds loopback and validates Host/Origin/token (`src/main.rs:126`, `crates/axon-bus/src/serve.rs:204`); local sends check edges (`crates/axon-bus/src/msg.rs:90`); peer bodies already carry an untrusted preface (`crates/axon-bus/src/msg.rs:454`); hook relays accept only specific shell commands and inject the local actor (`crates/axon-bus/src/relay.rs:41`, `crates/axon-bus/src/relay.rs:77`); audit appends are serialized (`crates/axon-bus/src/store.rs:225`). None substitutes for the new federation boundary. Protocol recommendations above are design choices, not claims that an untested Rust dependency integration is ready.

# 3. Missing acceptance criteria

The following behaviours are for an independent test writer **before implementation**. Use two isolated Axon data directories, controlled keys/clocks/network faults, two local projects P/Q, a worktree of P, a cross-project child, an observed-only session and a third unauthorized peer. Exercise the actual Settings/API → service → SQLite → real harness-hook payload path. Treat the numeric limits in section 2 as the proposed fixture contract. Every rejection must leave message/control-plane state unchanged, with bounded diagnostic evidence; it must not leak an ungranted project's name, path, agents or route. No acceptance tests were run during this review.

| ID / evidence | Input or fault | Expected observable result |
|---|---|---|
| A01 — F1; `crates/axon-bus/src/serve.rs:219` | Another OS account GETs the shell, then supplies its exposed legacy token and valid Host/Origin to Invite, Join, grant changes and `/api/msg` with a remote target. Also try peer-state GET and SSE. | No usable owner credential is disclosed or cached; all protected operations/streams return unauthorized/forbidden before metadata or writes. An authenticated owning browser succeeds. Wrong Host/Origin and an old browser session after restart remain rejected. |
| A02 — F1/F11; `src/main.rs:126` | A LAN peer attempts every existing dashboard/API path on the network listener, even with forged loopback Host/Origin headers. | The network listener offers only its authenticated federation protocol; it cannot reach dashboard, narrative, usage, end-session or human send APIs. Dashboard remains loopback-bound. |
| A03 — F5; `docs/reviews/P2P-COUNCIL-BRIEF.md:38` | Through Settings only, A creates a valid invitation, B joins, both confirm keys, and neither shares a project. | Each registry has the mutually confirmed identity with no grants; connected health appears, but discovery and messages are denied. No CLI/config edit is needed for ordinary pairing or project selection. |
